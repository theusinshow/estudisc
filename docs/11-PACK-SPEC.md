# 11 — Pack Specification

## Compatible Track Pack v2

ADR 0028 approves caderno.track.v2 alongside unchanged caderno.track.v1. v2 adds curriculum/prerequisites, sources, lesson metadata, shared Questions and exposure policy. Naming follows existing conventions; semantic validation checks all references, prerequisite cycles, question answers/provenance, registered interactions and reserved-item leakage. Preserve schema/packId/version/hash immutability and transactional import. The supplied minimal example is intentionally partial, not a published curriculum. See ifsc/integration/INTEGRATION-AND-PATCH-PLAN.md.

## Purpose

Packs are portable, versioned learning-content packages generated by trusted tools or external assistants and validated by KNOW/OS.

## Pack categories

- Track Pack
- Module Pack
- Lesson Pack
- Patch Pack
- Session Pack
- Context Pack
- Progress Pack
- Backup Pack

Content Packs and user-data Packs must not share implicit behavior.

## Schema naming

Initial schema identifiers retain the approved `caderno.*` namespace:

```text
caderno.track.v1
caderno.module.v1
caderno.lesson.v1
caderno.session.v1
caderno.context.v1
caderno.progress.v1
caderno.backup.v1
```

Changing this namespace requires an ADR and migration plan.

## Stable IDs

Examples:

```text
lessonId: js-fundamentals-001
conceptId: js-type-number
activityId: js-type-number-predict-001
```

Stable IDs are permanent within a publisher namespace. Display titles may change.

## Versioning

Each imported entity has a content version. Importing the same ID and version is idempotent. A newer version produces a diff. User progress and attempts remain separate and are never overwritten by content updates.

## Publication catalog

Publicly distributed Packs must be listed in `packs/catalog.json` before publication. Each catalog entry records:

- Pack `schema`;
- stable `packId`;
- integer content `version`;
- repository path;
- canonical content hash;
- compatibility metadata.

The tuple `schema:packId:version` is immutable. If any Pack content changes, publish a new integer `version`; do not reuse the same version with a different content hash. Run `pnpm packs:verify` before publication to validate the catalog, hash and compatibility metadata.

## Container

A future `.caderno` file may be a ZIP-compatible container:

```text
manifest.json
content/
assets/
```

V1 may also accept validated JSON during development. Binary or active content is prohibited.

## Validation

Required sequence: parse → schema validate → semantic validate → preview → version/diff analysis → conflict resolution → atomic apply.

See `packs/schemas/` and `packs/examples/` for draft fixtures.
